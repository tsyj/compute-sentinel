# SafeKill

终止进程的唯一入口。**不存在绕过本 Skill 的终止路径。**

## 为什么需要它

真实事故：在一台多用户共享的计算节点上，为清理自己的试跑进程，
用 `ps -eo pgid,comm | awk '$2=="<binary>"'` 取进程组批量 `kill -9 -PGID`。

问题在于——**同机另一位用户的 128 核生产作业用的是同名 binary**。
那条命令对他们的每一个进程组都发起了终止。

只因为跨用户 `kill` 会以 `EPERM` 静默失败，那个作业才幸存下来。
**权限边界是当时唯一的护栏，而它并不是我们设计的。**

结论：在共享集群上，按进程名匹配是不可接受的终止判据。

## 三重判据

必须**同时**满足，缺一拒绝：

| 判据 | 检查内容 | 拒绝理由示例 |
|---|---|---|
| **A · 属主** | 进程 `user` 必须等于发起人本人 | `进程属主 jiaxin ≠ 发起人 xinyuan，拒绝` |
| **B · 命令行** | `args` 必须匹配本次事故登记的输入文件名 | `目标 args 含 roms_mining_3mon_128cpu.in，与本事故登记的 roms_real.in 不符，拒绝` |
| **C · 进程组** | `PGID` 必须在事故开始时预登记的范围内 | `PGID 48211 不在登记范围 {51033, 51034}，拒绝` |

判据 B 是关键：**同名 binary 在共享集群上很常见，区分不同作业的是它读的输入文件，不是它的名字。**

## 输入

```json
{
  "target_spec": {
    "user": "必填，必须等于发起人",
    "args_contains": "必填，本次事故登记的输入文件名",
    "pgid_allowlist": [12345, 12346]
  },
  "reason": "自由文本，写入审计",
  "incident_id": "关联的事故 ID",
  "signal": "TERM | KILL",
  "dry_run": true
}
```

`dry_run` 默认为 `true`。首次调用只返回匹配结果，不执行。

## 输出

```json
{
  "matched_pids":  [{ "pid": 0, "user": "", "args": "", "pgid": 0 }],
  "refused_pids":  [{ "pid": 0, "reason": "属主不符 | args 不符 | PGID 不在登记范围" }],
  "executed": false,
  "audit_id": "string",
  "approval_message_id": "审批消息在协作房间中的 ID"
}
```

`refused_pids` 必须完整返回并写入审计——**被拒绝的目标比被终止的目标更重要**，
它们是判据生效的证据。

## 调用条件

由 Executor Agent 在恢复方案含终止动作时调用。任何其他 Agent 不得直接调用。

## 依赖

集群适配器提供 `ps -eo user,pid,pgid,args`。凭证由网关注入，本 Skill 不持有真实凭证。

## 失败处理

| 情况 | 处理 |
|---|---|
| 三重判据任一不满足 | 拒绝该目标，写审计，继续检查其余目标，**不中断** |
| 匹配到 0 个目标 | 返回空集，视为成功（幂等） |
| 部分终止后失败 | 记录已终止与未终止清单，不重试，升级给人工 |
| 审批超时 | 不执行，事故转人工，写审计 |

## 安全边界

- **风险等级恒为 L2**，无论目标多少个、无论 `signal` 是 TERM 还是 KILL
- 必须在 Incident Room 内取得人工审批，审批消息 ID 写入审计
- **跨用户目标恒拒绝**，不提供任何提权路径
- 首次调用强制 `dry_run`，人工看过匹配结果后才能实际执行
- 不接受 `pkill` / `killall` 式的名称匹配语义

## 复用价值

任何多用户共享的计算集群都需要这层护栏。判据表是纯配置，与具体 workload 无关。

## 与多 Agent 流程的关系

Planner 生成的方案若含终止动作，该动作被强制标记 L2；
Executor 调用本 Skill 先做 `dry_run`，把匹配与拒绝清单发到 Incident Room；
人工确认后 Executor 再以 `dry_run: false` 执行；
Curator 在复盘中把新出现的误伤模式写回判据表。
