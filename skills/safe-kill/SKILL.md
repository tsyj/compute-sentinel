# SafeKill

终止进程的唯一入口。**不存在绕过本 Skill 的终止路径。**

## 为什么需要它

真实事故：在一台多用户共享的计算节点上，为清理自己的试跑进程，
用 `ps -eo pgid,comm | awk '$2=="<binary>"'` 取进程组批量 `kill -9 -PGID`。

问题在于——**同机另一位用户的 128 核生产作业用的是同名 binary**。
那条命令对他们的每一个进程组都发起了终止。

只因为跨用户 `kill` 会以 `EPERM` 静默失败，那个作业才幸存下来。
**权限边界是当时唯一的护栏，而它并不是我们设计的。**

结论：在共享集群上，按进程名匹配是不可接受的终止判据。

## 三重判据

必须**同时**满足，缺一拒绝：

| 判据 | 检查内容 | 拒绝理由示例 |
|---|---|---|
| **A · 属主** | 进程 `user` 必须等于发起人本人 | `进程属主 jiaxin ≠ 发起人 xinyuan，拒绝` |
| **B · 命令行** | `args` 必须匹配本次事故登记的输入文件名 | `目标 args 含 roms_mining_3mon_128cpu.in，与本事故登记的 roms_real.in 不符，拒绝` |
| **C · 进程组** | `PGID` 必须在事故开始时预登记的范围内 | `PGID 48211 不在登记范围 {51033, 51034}，拒绝` |

判据 B 是关键：**同名 binary 在共享集群上很常见，区分不同作业的是它读的输入文件，不是它的名字。**

## 输入

```json
{
  "target_spec": {
    "user": "必填，必须等于发起人",
    "args_contains": "必填，本次事故登记的输入文件名",
    "pgid_allowlist": [12345, 12346]
  },
  "reason": "自由文本，写入审计",
  "incident_id": "关联的事故 ID",
  "signal": "TERM | KILL",
  "dry_run": true
}
```

`dry_run` 默认为 `true`。首次调用只返回匹配结果，不执行。

## 输出

```json
{
  "matched_pids":  [{ "pid": 0, "user": "", "args": "", "pgid": 0 }],
  "refused_pids":  [{ "pid": 0, "reason": "属主不符 | args 不符 | PGID 不在登记范围" }],
  "executed": false,
  "audit_id": "string",
  "approval_message_id": "审批消息在协作房间中的 ID"
}
```

`refused_pids` 必须完整返回并写入审计——**被拒绝的目标比被终止的目标更重要**，
它们是判据生效的证据。

## 调用条件

由 Executor Agent 在恢复方案含终止动作时调用。任何其他 Agent 不得直接调用。

## 依赖

集群适配器提供 `ps -eo user,pid,pgid,args`。凭证由网关注入，本 Skill 不持有真实凭证。

## 失败处理

| 情况 | 处理 |
|---|---|
| 三重判据任一不满足 | 拒绝该目标，写审计，继续检查其余目标，**不中断** |
| 匹配到 0 个目标 | 返回空集，视为成功（幂等） |
| 部分终止后失败 | 记录已终止与未终止清单，不重试，升级给人工 |
| 审批超时 | 不执行，事故转人工，写审计 |

## 安全边界

- **风险等级恒为 L2**，无论目标多少个、无论 `signal` 是 TERM 还是 KILL
- 必须在 Incident Room 内取得人工审批，审批消息 ID 写入审计
- **跨用户目标恒拒绝**，不提供任何提权路径
- 首次调用强制 `dry_run`，人工看过匹配结果后才能实际执行
- 不接受 `pkill` / `killall` 式的名称匹配语义

## 复用价值

任何多用户共享的计算集群都需要这层护栏。判据表是纯配置，与具体 workload 无关。

## 与多 Agent 流程的关系

Planner 生成的方案若含终止动作，该动作被强制标记 L2；
Executor 调用本 Skill 先做 `dry_run`，把匹配与拒绝清单发到 Incident Room；
人工确认后 Executor 再以 `dry_run: false` 执行；
Curator 在复盘中把新出现的误伤模式写回判据表。

## 版本与演进

**本 Skill 的版本策略与其他 Skill 不同：判据只增不减。**

| 变更类型 | 是否允许 | 说明 |
|---|---|---|
| 新增一条拒绝判据 | ✅ minor | 收紧永远安全 |
| 收紧已有判据 | ✅ minor | 同上 |
| **放宽或删除任何一条判据** | ⚠️ **major，且需双人 review** | 每一条判据背后都是一次真实事故 |
| 三重判据改为可配置开关 | ❌ **不允许** | 可关闭的安全机制等于没有 |

**为什么这样定**：安全类 Skill 的失效模式是不对称的 —— 判据过严只会带来一次多余的人工确认，
判据过松可能毁掉别人跑了一个月的作业。因此把「放宽」这个方向的变更成本刻意抬高。

**发布**：与其他 Skill 一样走 PR + review，但额外要求变更说明里写清楚
「这条判据放宽后，案例 02 里的哪一种误伤会重新变为可能」。

**回滚**：改标签回退。但**回退到更宽松的版本视同放宽判据**，同样需要双人确认。

## 能力评估

**不用统计指标评估。**准确率 99% 对这个 Skill 是失败 —— 剩下的 1% 就是别人的 128 核作业。

### 评估方式：对抗测试，全通过才算合格

构造一组**必须被拒绝**的目标，验证拒绝率为 100%：

| 对抗用例 | 构造方式 | 期望 |
|---|---|---|
| 跨用户同名进程 | 另一账号跑同名 binary | 拒绝，理由为「属主不符」 |
| **同名 binary 不同作业** | `coawstM_yagi_AB_fixed` 与 `AB_buggy` 同时在跑 | 只匹配 args 登记的那个，另一个拒绝 |
| PGID 越界 | 事故登记后新起的同类进程 | 拒绝，理由为「PGID 不在登记范围」 |
| 名称匹配语义 | 传入 `pkill` 风格的模式串 | 拒绝，本 Skill 不接受名称匹配 |
| 空匹配 | 目标已自行退出 | 返回空集视为成功（幂等），不报错 |
| 未审批直接执行 | 跳过审批调用 `dry_run: false` | 拒绝执行，写审计 |

**通过标准：以上全部通过。任何一条失败即视为该版本不可发布。**

### 常态化验证

- 每次 PR 必跑对抗测试集，一条不过即阻断合并
- 每一次真实调用的 `refused_pids` 全量入审计 —— 生产环境里的拒绝记录本身就是持续验证的证据
- Curator 在复盘中发现新的误伤模式时，**先补一条对抗用例，再补判据**

### 一个刻意的设计取舍

本 Skill 不追求「尽量帮用户把该杀的都杀掉」。
匹配不确定时**宁可少杀、让人工介入**，也不做启发式扩大匹配。
案例 02 里那次事故的性质就是「启发式匹配 + 批量操作」，这个方向不再走第二次。

### 已跑过的评估（2026-08-16）

对抗测试集已实现并执行：`tools/test_safe_kill.py`（纯标准库，`./verify.sh` 每次必跑）。
被测对象是 `tools/safe_kill.py` 的目标选择器 —— **该模块不杀任何进程**，
只回答"哪些可以操作、哪些必须拒绝、理由是什么"，真正的终止由 Executor 在人工审批后执行。

| 对抗用例 | 结果 |
|---|---|
| 跨用户同名进程（他人 128 核作业） | ✅ 拒绝，理由「属主不符」 |
| 同名 binary 不同作业 | ✅ 拒绝，理由「命令行未包含登记的输入文件」 |
| PGID 越界（登记后新起的同类进程） | ✅ 拒绝，理由「PGID 不在登记范围内」 |
| 名称匹配语义（`coawstM*` / `-f` / `coawst?` / `coawstM[12]`） | ✅ 整次调用作废，无任何放行项 |
| 空匹配（目标已自行退出） | ✅ 幂等成功，不报错 |
| 登记不完整（缺 owner / input_file / pgids） | ✅ 整次作废 |
| 三条判据只满足两条 | ✅ 拒绝（缺一即拒） |

**21 项断言全部通过。** 按本节的通过标准（全过才可发布），当前版本合格。

最关键的是第一条：真实事故里，另一位用户那个 128 核作业是**靠跨用户 kill 的
EPERM 静默失败才幸存的**——权限边界当时是唯一一道墙。现在它在判据层就被明确拒绝，
且给出可审计的理由，不再依赖运气。

**已知局限**：对抗用例是依据 case-02 的现场形态构造的，
覆盖的是"同名 binary 混淆"这一类误伤。其他误伤模式（如容器内 PID 命名空间错位、
作业调度器重用 PGID）尚未构造用例。
