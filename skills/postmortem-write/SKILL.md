# postmortem write

> 规格草案。字段按赛道一参赛手册附录 B「Skill 清单模板」组织，
> 完整输入输出 Schema、失败处理与判据表在复赛阶段补齐。

## 使用场景

事故闭环后生成复盘，把新故障模式写回 Runbook，为 crash-triage 提新判据、为 safe-kill 提新护栏。知识入库走 PR，需人工 review。

## 输入 / 输出

待定稿。

## 调用条件

待定稿。

## 依赖工具 / 系统

集群适配器（MCP 或等价集成契约）。凭证由网关注入，Skill 不持有真实凭证。

## 失败处理

统一原则：**证据不足时输出"缺什么"，不猜、不编造结论。**

## 权限与安全

风险等级 L1。分级定义见 [README](../../README.md#安全分级)。

## 复用价值

领域差异收敛到 adapter 配置，Skill 逻辑与 workload 无关。

## 版本与演进

复盘模板与产出格式计版。输出的**新判据 PR** 本身不由本 Skill 计版 ——
它进入 `crash-triage` / `config-precheck` / `safe-kill` 各自的判据库，按那边的规则计版。

本 Skill 的权限边界不随版本放宽：**任何版本都只提 PR，不直接写入知识库或修改线上 Skill。**

## 能力评估

这是唯一以**人工评审为主**的 Skill，因为「复盘写得好不好」没有可自动化的真值。

| 指标 | 评估方式 |
|---|---|
| 时间线准确率 | 与原始日志时间戳比对，可自动化 |
| 证据引用完整率 | 每个结论是否挂了具体文件与行号，可自动化 |
| **新判据被接受率** | 提出的判据经人工 review 后被合入的比例 —— 这是最有意义的指标 |
| 复盘可读性 | 人工评分，领域专家能否直接看懂并采纳 |

第三项刻意选作核心指标：一份没有产出任何可复用判据的复盘，
无论写得多漂亮，都没有完成「把事故变成能力」这件事。

反指标：**被 review 打回的判据中，属于「过度泛化」的比例**。
从单次事故推出过宽的规则，会污染判据库并制造大量误报。
