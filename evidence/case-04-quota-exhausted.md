# 证据案例 04 · 配额耗尽：一次发生在我们自己身上的"心跳全绿但干不了活"

> 2026-08-16 03:30–03:45，为 Executor 的 L2 审批闭环做实跑时撞上。
> 不是演练，是真事故。

---

## 现象

向 Executor 投递一个 L2 恢复动作后，房间里只回了两个字：

```
[03:30:32] executor: Internal error
```

排查路径（这一段本身就说明了问题）：

| 步骤 | 观察 | 结论 |
|---|---|---|
| `docker ps` | 4 个 Worker 全部 `Up`，状态健康 | 看不出问题 |
| `agt get workers` | 全部 `Running` | 看不出问题 |
| `docker logs` | 只有例行轮询，**没有任何错误栈** | 看不出问题 |
| 从容器内直接打网关 | **HTTP 429 `insufficient_quota`** | 找到了 |

```
$ curl -s $AGENTTEAMS_AI_GATEWAY_URL/v1/chat/completions -H "Authorization: Bearer $KEY" …
HTTP 429
{"error":{"message":"Your token-plan 1-week quota has been exhausted.
  The quota will reset at 08-15 21:24:00 UTC.","type":"insufficient_quota"}}
```

## 为什么这条证据值得留

**这正是本项目立项要解决的那类故障，只不过发生在我们自己的 Agent 系统上。**

- 进程都在、容器都 `Up`、编排层报 `Running` —— **心跳级检查全绿**
- 但系统**一件事也做不成**，而且没有任何一层主动告诉你为什么
- 唯一的信号是"回复内容变成了 `Internal error`"，这是**语义级**信号，不是心跳级信号
- 排查花了约 15 分钟，其中 12 分钟浪费在"看起来都正常"的三层检查上

对照 README 开篇那句话：

> 现有运维只做心跳级检查——活着就算健康。

我们自己的 Agent 系统当时就处在这个状态。

## 它暴露的两个真实缺口

### 一、Worker 把上游 429 吞成了 `Internal error`

配额耗尽是**可恢复、有明确恢复时间**的状态，上游连恢复时刻都返回了
（`reset at 08-15 21:24:00 UTC`）。但 Worker 把它压成了一句 `Internal error`，
既没有区分"配额耗尽"与"真的内部错误"，也没有把恢复时间透出来。

正确的行为应该是：把 429 与恢复时间原样呈现，让人知道**等一会儿就好**，
而不是去查一遍容器、日志和编排状态。

> 这一条已加入 `docs/upstream-issues.md` 的候选清单。

### 二、我们自己的可观测采集没覆盖"模型调用失败"

`measure-05` 采的 56 个 span 全部是**工具调用**（Bash / Read / Glob），
`by_decision` 全是 `allow`。**模型调用本身的成败不在审计库里**——
所以这次 429 在我们的可观测体系里是**完全不可见的**。

这与 `docs/requirements-mapping.md` 里 9.3 一节如实标注的缺口对上了：

> Tool 成功率 ⚠️ 只有决策层成功率；Token 消耗 ❌ 未采

如果当时有 Token/调用成功率的 Metrics，这次故障应该是**秒级定位**而不是 15 分钟。

## 与赛程相关的风险披露

本项目使用的阿里云百炼 **Token Plan 套餐按周计配额**，且**整体套餐 2026-09-10 到期**，
而决赛在 **2026-09-22**。也就是说：

**决赛当天，本方案的默认模型通道可能是不可用的。**

这不是假设，今晚已经实测撞到过一次同类问题（周配额）。应对：

| 措施 | 状态 |
|---|---|
| 备用供应商（DeepSeek）密钥可用性 | ✅ 已验证：`/v1/models` 返回 200，一次真实补全成功 |
| 跨供应商迁移成本 | ⚠️ **实测比预估贵**：需协调修改 3 个 Higress 托管资源（`wasmplugins/ai-proxy.internal.yaml`、`mcpbridges/default.yaml`、`ingresses/ai-route-*.yaml`），且首个文件带有 `PLEASE DO NOT EDIT DIRECTLY` 注记 |
| 同套餐内换模型 | ✅ 仅改模型名，已实测 5 个备选可用 |

> **口径更正**：此前材料里说过"切换成本就是改一个环境变量"。
> 那句话只对**同套餐内换模型**成立。**跨供应商切换**是三个资源协调修改 + 容器重建，
> 完全是另一回事。已在 README 与本文件中区分开。

**判定逻辑不受影响**：`decide()` 是纯规则、不调模型，
`./verify.sh` 的 11 项断言在配额耗尽期间**全部照常通过**。
受影响的只有 Agent 的自然语言推理部分。这也正是我们坚持
"不赌模型做根因、把判定做成确定性规则"的原因之一。

## 处置

配额于北京时间 05:24 自动恢复，未做任何破坏性变更。

**当时考虑过但主动放弃的一条捷径**：把 Executor 直接指向 DeepSeek、绕过 Higress 网关。
放弃的理由是——那样 Worker 就会直接持有真实 API Key，
而"真实凭证只存在于网关侧、Worker 拿不到"正是
[case-03](case-03-agentteams-deployment.md) 用 401/200 对照实验证明过的性质。
为了赶时间去破坏自己刚验证过的安全边界，还会在审计记录里留下一个持有真凭证的 Worker，
不划算。**赶时间不是降低安全标准的理由，演练时养成的习惯会原样带到生产。**
