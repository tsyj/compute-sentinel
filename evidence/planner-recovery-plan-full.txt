### 回答你的三个问题

**Q1：中途死了 vs 正常跑完但没产出该产出的东西？**

**后者（正常跑完但缺产物）。** 与 Sentinel 判定一致。

**Q2：为什么？**

根因链（triage 归类，我补充配置层面的精确分析）：

1. Bridge 从 `wrfrst_d01_2024-09-06_00:00:00` 做 hot-restart（`bridge_v3.excerpt.log:3379-3382`，4 个 MPI rank 各读一次）
2. WRF hot-restart 从该 restart 文件**恢复了 write-restart alarm = 720 min**（production 的 restart_interval）
3. Bridge 窗口 = 542 min < 720 min → alarm 永远不会响 → wrfrst 永远不会写入
4. v3 尝试 `override_restart_timers=.true.` 覆盖 alarm：
   - **对 history alarm 成功**：v2 wrfout 首帧@01:00（720-min 恢复值），v3 wrfout 首帧@03:00（namelist `history_interval=180`）
   - **对 restart alarm 失败**：wrfrst 文件数仍为 0
5. 结论：此 WRF build 的 `override_restart_timers` 实现**只覆盖 history alarm，不覆盖 restart alarm**

**Q3：能不能续跑？**

```
resumable: no
```

**原因：不存在有效的续跑断点。**

- wrfrst_d01_2024-09-06_09:00:00 **从未被写入** — 这是链条要求的 09:00 三模型同步点
- v3 的 ROMS restart (`yagi_rst.nc` 09) 和 SWAN restart (`swan_rst.dat` @09:00) 虽然存在，但 **WRF 没有对应的 restart 文件**
- WRF 无法从 wrfout（history 文件）做 hot-restart — 它需要 wrfrst（restart 文件）
- 没有 WRF restart → 下一段耦合无法初始化 WRF → 链条无法继续

**缺什么才能续跑：** 一个在 09:00（或窗口内任何时刻）的合法 `wrfrst` 文件。当前没有任何路径能获得它——除非修复配置后重跑 bridge。
