# measure-12 · Token 消耗与 Tool 成功率：手册点名的两个指标

> 2026-08-16
> 补的是 `docs/requirements-mapping.md` 里 9.3 一节的两个 ❌ / ⚠️。

---

## 为什么这份是"自己测"而不是"从系统里取"

手册 9.3 明确点名 Metrics 应覆盖 **Token 消耗**与 **Tool 成功率**。
我们先去找现成的：

| 找过的地方 | 结果 |
|---|---|
| Higress 网关访问日志 `/var/log/higress/` | **空目录**，无记录 |
| Worker 治理审计库 `audit_events` 表 | 字段只有 `ts / workspace_dir / agent_id / session_id / tool_name / target / decision / reason / extra` —— **没有 token 字段**，且只记工具调用，不记模型调用 |
| controller 日志 | 无 usage 记录 |

**结论：框架本身不记录 token。** 这坐实了此前标注的 ❌ ——
不是我们没去采，是这条链路上没有人记账。

> 这也解释了 [case-04](case-04-quota-exhausted.md) 里配额耗尽为什么排查了 15 分钟：
> 如果有 token 计量，那次故障应该是秒级定位。

所以本文档的数字是**我们自己实测的**，方法写在下面，可复现。

---

## 一、Token 消耗

### 测法

用 **Executor 的真实 SOUL**（4042 字节）作为 system prompt，
真实事故文本作为首轮 user 消息，经 **Higress 网关**（与 Worker 完全同一条链路）
调 `qwen3.7-plus`，读返回的 `usage` 字段。

随后模拟真实的工具往返：每轮把上一轮的助手回复 + 一条真实的工具输出
（预检结果、备份 md5、文件内容、二次预检结果）追加进上下文，再调一次。

### 单轮成本

```
prompt_tokens      1163
completion_tokens   392   （其中推理 token 244）
total_tokens       1555
```

### 多轮增长（一次完整 L2 处置的形状）

| 轮 | prompt | completion | 其中推理 | 累计 total |
|---:|---:|---:|---:|---:|
| 1 | 1126 | 319 | 145 | 1445 |
| 2 | 1366 | 183 | 76 | 2994 |
| 3 | 1515 | 224 | 83 | 4733 |
| 4 | 1678 | 592 | 414 | 7003 |
| 5 | 1896 | 1009 | 848 | **9908** |

**5 轮累计 9908 tokens**（prompt 7581 + completion 2327）。

两个值得注意的形状：

1. **prompt 每轮增长约 190 tokens** —— 工具结果不断累积进上下文。
   这意味着长事故的成本是**超线性**的，不是轮数 × 单价。
2. **推理 token 占 completion 的 36%–84%**，且在最后一轮（写审批报告）飙到 848。
   `qwen3.7-plus` 的推理开销不容忽略，换成非推理模型成本结构会完全不同。

### 一次真实事故的实际规模

从 Matrix 房间统计本次实跑的实际轮次（每条 Worker 消息 ≈ 一次补全）：

| 事故 | Agent | 轮次 |
|---|---|---|
| incident-002（L2 批准） | executor | 17 |
| incident-003（L2 拒绝） | executor | 22 |
| incident-002（验证） | verifier | 17 |
| incident-005（阴性验证） | verifier | 10 |

**按实测的增长曲线外推，一次完整的 L2 处置（Executor 17 轮 + Verifier 17 轮）
量级在 5 万–8 万 tokens。**

> ⚠️ 这是**外推值，不是实测值**。实测只做到 5 轮；
> 第 6 轮之后 prompt 继续累积，实际可能高于线性外推。
> 标为估算，不写成实测数字。

### 与"人工处理一次"的对照 —— 我们没有这个数

手册关心成本，但**"比人工便宜多少"这个问题我们答不了**，因为缺人工侧基线。
唯一能对照的是 [case-01](case-01-wrf-restart-alarm.md) 里那次真实事故：
人工诊断链路约 45 分钟读源码 + 两次共 4 小时 32 分钟的 160 核重跑。

拿"几万 tokens"去比"4.5 小时 160 核机时"是不严谨的 ——
**两者的单位不可通约，我们不做这个换算**。真正该测的是
"引入本系统后，同类事故的平均恢复时间与重跑次数是否下降"，
那需要长期运行数据，目前没有。

## 二、Tool 成功率

从本次实跑的完整 Matrix 记录中统计所有工具调用：

| 工具 | 次数 |
|---|---|
| `execute_shell_command` | 14 |
| `read_file` | 5 |
| `glob_search` | 3 |
| `edit_file` | 1 |
| **合计** | **23** |

| 指标 | 值 |
|---|---|
| 被沙箱拦截 | **1**（4.3%） |
| 执行报错 | 0 |
| **Tool 成功率** | **95.7%** |

唯一那次拦截是 [measure-10](measure-10-l2-approval.md) 里 Executor 想 `rm` 掉回滚点，
被框架沙箱以 `[HIGH] Shell command contains 'rm'` 拦下。

**这次"失败"是护栏正常工作，不是缺陷。** 因此 95.7% 这个数字要这样读：
**没有一次工具调用是因为写错命令、路径错误或权限不足而失败的**；
唯一的非成功是安全策略主动阻断。

> 区别于 `audit_events` 里的 `by_decision: allow 56/56 = 100%` ——
> 那是**决策层**成功率（网关有没有放行），不反映工具本身执行成败。
> 本文档给的是执行层。两个都要有，含义不同。

## 仍然没有的（不隐瞒）

1. **TTFT（首 token 时延）**未采。框架审计库不记录，我们的测法也拿不到 ——
   需要流式调用才能测。
2. **一次事故的 token 总量是外推值**，不是端到端实测。
   要实测需要在网关侧加计量，那是一个改动而不是一次测量。
3. **无人工侧成本基线**，因此"省了多少钱"无法回答。
4. 样本极小：23 次工具调用、4 次事故。**95.7% 这个数不具统计意义**，
   它说明的是"这几次里没有工具执行失败"，不是"成功率是 95.7%"。
