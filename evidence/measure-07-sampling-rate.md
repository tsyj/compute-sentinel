# measure-07 · 对照实验：采样周期决定了能不能用上快速通道

> 2026-08-15　RTX 4090　｜　与 [measure-06](measure-06-gpu-stall.md) 同一套脚本，只改采样密度与工作相位长度
> 原始数据：[`gpu-stall/runB-*`](gpu-stall/)

---

## 这一跑要回答什么

measure-06 里有一条没被触发的判据：`adapters/pytorch.json` 的 `degraded_stall_sec = 300`。

设计意图是——一旦确认「GPU 曾经忙过」（说明数据预处理已结束），此后再出现
「CPU 打满 + GPU 闲置」就可以用更短的 300 秒阈值告警，不必等通用的 900 秒。

但 measure-06 全程 `gpu_ever_busy = False`，判定退回了 900 秒。
**原因不是判据错，是采不到**：三个好 epoch 总共只跑了 16 秒，而采样周期是 20 秒。

这一跑把工作相位拉长（10 epoch × 200 step）、采样加密（20s → 10s），验证同一份判据。

## 结果

| | measure-06（跑 A） | measure-07（跑 B） |
|---|---|---|
| 好 epoch | 3 × 60 步，共 **16 秒** | 10 × 200 步，共 **约 65 秒** |
| 采样周期 | 20 秒 | **10 秒** |
| 快照总数 | 65 | 63 |
| 采到 GPU 忙的快照 | **0 个** | **4 个**（87% / 88% / 87% / 13%） |
| `gpu_ever_busy` | 始终 False | **True** |
| 生效阈值 | 900 秒（通用） | **300 秒（快速通道）** |
| 修复前 | 全程漏报 | 全程漏报 |
| 修复后发现时延 | 909 秒（15.2 分钟） | **318 秒（5.3 分钟）** |

```
→ 首次判定 STALLED: 23:29:35，距退化开始 318s（5.3 分钟）
退化路径开始（日志最后一条进度行）: [23:24:17] ep 11 begin
```

判据本身没改一行代码，**发现时延缩短到原来的三分之一，差别全部来自采样密度**。

## 两条比时延数字更重要的观察

### 一、GPU 利用率是脉冲式的，采样天然会漏

即使采样加密到 10 秒、GPU 工作相位长达约 65 秒，**63 个快照里也只有 4 个采到了 GPU 忙**。

原因是每个 epoch 结束要写一个 537 MB 的 checkpoint，落盘期间 GPU 是闲的。
真实训练里同样普遍：数据加载、checkpoint、日志同步、梯度同步等待，
都会让 GPU util 瞬时掉到 0。

**推论**：`gpu_ever_busy` 这种"曾经忙过就 latch 住"的**单向状态位**是对的设计 ——
如果换成"最近 N 次采样的 GPU 均值"，脉冲式负载会被平均成低值，反而制造误判。
反过来，任何**要求 GPU 持续高占用**才判健康的规则都会大量误报。

### 二、显存不是可用的健康信号

卡死期间的 **54 个快照，显存全部恰好是 3294 MiB、GPU 利用率全部恰好是 0** ——
与正常训练时的显存占用完全一致。直到进程真正退出，显存才掉回 188 MiB：

```
23:23:20  gpu= 87%  mem=3294MiB   ← 正常训练
23:30:52  gpu=  0%  mem=3294MiB   ← 卡死中，CPU 99.1%
23:31:14  gpu=  0%  mem=3294MiB   ← 卡死中，CPU 99.9%
23:34:21  gpu=  0%  mem= 188MiB   ← 进程退出，显存这才释放
```

CUDA context 不释放，显存就一直挂着。**只看显存占用的健康检查，在这类故障上永远是绿的。**
这与"进程存活"、"CPU 占用"是同一类错误：把**资源被占着**当成了**任务在推进**。

## 由此产生的运维准则

写进了 `skills/progress-probe/SKILL.md` 的能力评估一节：

1. **采样周期必须细于该 workload 的最短工作相位**，否则整个相位可能被跳过。
   对 GPU 训练，工作相位可以短到一个 epoch；建议采样周期 ≤ 10 秒。
2. 采不到不等于没有 —— `gpu_ever_busy` 只做**单向置位**，绝不因为"最近没采到"而复位。
3. 阈值收紧（`degraded_stall_sec`）**必须有前置条件**。本项目的前置条件是
   `gpu_ever_busy == True`，即已确认过了预处理阶段。没有这个前提，
   短阈值会把正常的数据预处理打成卡死。

## 局限

- 与 measure-06 同样是**构造的复现**，不是生产事故现场。
- 单卡。多卡场景下 `nvidia-smi` 取的是各卡最大值，
  "部分 rank 卡住而其他 rank 仍在算"的情形本判据**覆盖不到**，需要 per-rank 采集。
- 63 个快照中 4 个 GPU-忙，是小样本，"采样命中率"这个数字不具统计意义，
  它说明的是**现象存在**（脉冲式负载会被采样漏过），不是**发生频率**。
