## 一、误报率

### 测法

测误报需要**真值恒为"正常运行"的样本** —— 也就是**成功跑完**的历史作业。
`tools/replay_from_log.py` 从历史日志重建信号快照序列：长时作业的日志里带着自己的时间信息
（WRF 的每步 `elapsed seconds`、wget 进度行的累计字节与速率），
据此还原出「墙钟时刻 → 日志字节偏移」的映射，再按采样周期切片。

**日志字节数是真的，时间轴是日志自己写的，不是我们编的。**

> **重建方法的自校验**：下载任务重建出的总时长是 **4.29 小时**，
> 而日志首尾的真实墙钟是 06:58:40 → 11:15:52 = **4.287 小时** —— 误差 0.1%。
> 这说明这套时间轴还原是可信的。

两份样本都**没有**产物 mtime 序列（历史目录只剩最终状态），所以文件信号标为"不可采"。
这让判定少一票进展票，**更容易喊卡死** —— 也就是说这个默认让误报测试**更严格**，不是更宽松。

### 样本 A · COAWST 耦合模式，33.79 小时，成功跑完

WRF-ROMS-SWAN 三模式耦合，28800 个进度点，日志最长静默 316.8 秒。

| 采样周期 ↓ / `stall_sec` → | 60s | 120s | 300s | 600s | 900s | **1800s（当前值）** |
|---|---|---|---|---|---|---|
| 30s | 2.22% | 1.48% | 0.05% | 0% | 0% | **0%** |
| 60s | 2.27% | 1.48% | 0.05% | 0% | 0% | **0%** |
| 120s | 1.48% | 1.48% | 0% | 0% | 0% | **0%** |
| 300s | 0% | 0% | 0% | 0% | 0% | **0%** |

### 样本 B · 18 GB 数据集下载，4.29 小时，成功完成

wget 拉 `Global_Argo_TS_dataset.tar.gz`，351824 个进度点。

**全部采样周期 × 全部阈值组合，误报 0 次。**

这同时验证了 `adapters/download.json` 的一个刻意设计：
`progress_line_regex` 被设成 `$^`（永不匹配），因为下载日志的"进度"不在文字里。
判定完全依靠产物字节增长 —— 实测证明这个选择是对的。

### 结论

| 结论 | 数字 |
|---|---|
| 两个 adapter 的当前阈值下 | **误报 0 次 / 38.1 小时真实运行**（本文档的两份样本；加上 [measure-09](measure-09-baseline.md) 的 GPU 训练负样本后累计 **40.6 小时**） |
| 误报归零的最小阈值（COAWST，30–60s 采样） | **600 秒** |
| 当前值 1800 秒相对该边界的裕量 | **3 倍** |

**阈值调低到 60 秒会付出 2.2% 的误报**。按 30 秒采样、一天 2880 次判定算，
那是每天约 64 次假告警 —— 一周之内没人会再看这个告警。
这就是"宁可晚报，不可错报"具体值多少钱。

## 二、把漏报和误报放在一起看

这才是选工作点的依据：

| `stall_sec` | 误报率（COAWST 33.8h 真实运行） | 漏报时延（GPU 退化路径） |
|---|---|---|
| 300 | 0.05% | **318 秒** ← pytorch 快速通道用的就是这档 |
| 600 | **0%** | ~610 秒 |
| 900 | 0% | **909 秒**（measure-06 实测） |
| 1800 | 0% | ~1810 秒 ← coawst 当前值 |

两类 workload 取了不同的工作点，**这是有意的**：

- **COAWST / WRF** 取 1800 秒。它们的正常静默本来就长，且一次误停重跑的代价是几小时机时。
- **PyTorch 退化路径** 取 300 秒。这一档在 CPU 型 workload 上有 0.05% 误报，
  但 pytorch 的 300 秒**只在退化画像成立时才启用**（CPU 打满 + GPU 闲置 + 本次运行 GPU 曾经忙过），
  这个条件比"日志静默"具体得多，触发面窄得多。

## 三、性能

### 单次调用开销

```
probe_job_progress 单次判定            中位   0.33 ms    P90   0.35 ms
stat_outputs（1.8 GB 目录）           中位   0.27 ms    P90   0.29 ms
tail_log                              中位   0.06 ms    P90   0.07 ms
sample_resources（全机 ps 扫描）       中位 108.14 ms    P90 117.86 ms   ← 慢了 300 倍
```

判定本身是纯 IO + 正则，微秒级不是瓶颈。**唯一的瓶颈是资源信号要扫全机进程表。**

### 发现并修掉的扩展性缺陷

原实现**每判定一个作业就扫一次全机进程表**。
盯 N 个作业 = 每轮 N 次全机扫描 —— 这是整套判定里**唯一随作业数线性劣化**的地方。

同一轮巡检内进程表几乎不变，因此给 `ps` 快照加了 2 秒 TTL 缓存，让同轮的所有作业共用一次扫描。
TTL 取 2 秒而非更长：巡检周期是分钟级，2 秒足够覆盖一轮扇出，又不会让相邻两轮读到陈旧数据。

| 作业数 N | 优化前 | 优化后 | 加速 |
|---|---|---|---|
| 1 | 108 ms | 108 ms | 1.0× |
| 10 | 1093 ms | 116 ms | **9.4×** |
| 50 | 5538 ms | 147 ms | **37.8×** |
| 100 | **11005 ms** | **189 ms** | **58.1×** |

盯 100 个作业，一轮巡检从 **11 秒降到 0.19 秒**。

安全边界未受影响：`BAD_PATTERN` 校验发生在读缓存**之前**，
`'; rm -rf /'`、`'$(whoami)'`、超长串三类注入串实测仍被拒。

### 回放吞吐

65 个快照 × 两种判定模式，墙钟 **0.23 秒**，峰值内存 **47 MB**，纯标准库、不调模型。

### 三 Agent 闭环的真实耗时

从 `evidence/observability-snapshot.json` 的 56 个 span 算出：

| Worker | 工具调用 | 活跃跨度 | 相邻调用间隔（中位 / P90） |
|---|---|---|---|
| sentinel | 15 | 7.5 分钟 | 3.4s / 10.6s |
| triage | 31 | 2.5 分钟 | 0.0s / 5.4s |
| planner | 10 | 1.1 分钟 | 0.0s / 52.2s |

端到端墙钟 65.2 分钟，但**这个数字不能当性能指标** ——
中间大段是操作者读输出、投递下一条消息的人工时间。Agent 活跃时间合计约 11 分钟。

## 仍然没有的数字（不隐瞒）

1. **GPU 训练场景的误报率**。误报测的是 CPU 型 workload（COAWST、下载），
   训练作业的正常静默分布可能不同。缺一份成功跑完的训练日志。
2. **Token / 成本**。一次事故要烧多少钱、比人工便宜多少 —— 没测。
3. **与基线的对照**。没有和人工巡检或现有监控工具做过对照实验。
4. **Executor / Verifier / Curator 的性能**：这三个 Agent 还没跑过，无从谈起。
5. 误报样本只有 2 个作业、2 类 workload、来自同一集群同一团队。
   38.1 小时是真实的，但样本多样性不足以谈"泛化"。

## 复现

```bash
# 误报扫描（不需要 GPU，不调模型）
python3 tools/replay_from_log.py --log <历史日志> --workload coawst \
    --elapsed-regex 'Timing for main:.*?:\s+([\d.]+) elapsed seconds' \
    --interval 60 --sweep

python3 tools/replay_from_log.py --log <wget日志> --workload download --wget \
    --interval 60 --sweep
```

> 日志来自本团队的历史科研运行，含主机路径等信息，**未随仓库发布**；
> 本文档给出的是脱敏后的统计结果与复现命令。
