# measure-11 · Verifier 实跑：阳性通过、阴性识破，但一次说对了结论说错了机制

> 2026-08-16 14:47–14:48
> 这份文档补的是闭环八步的**第 5 步「结果验证」** —— 在此之前它是仅存的 ❌。

---

## 为什么需要一个独立的 Verifier

measure-10 里 Executor 改完配置后自己重跑了预检，报告"验证通过"。
**但自己改完自己验，等于没验。**

Verifier 的职责就是不采信这句话，只看现场事实。
它的 SOUL 里第一句就是：

> Executor 说"我改完了、我验过了"。**你的存在就是因为这句话不能算数。**

风险上限 **L0，纯只读，无任何写权限**。

## 它做了什么

投递时**只给了 Executor 的自述，明确标注"这只是待验证的声明，不是证据"**，
没有告诉它结论对不对。它自己走完了六项清单：

| 步骤 | 它自己做的事 |
|---|---|
| 1 改动落盘 | `read_file` 读原文件，看到第 16 行 `restart_interval = 180,` |
| 2 与声称一致 | 跑 `diff` 备份 vs 当前，确认**仅第 16 行一处变更** |
| 3 回滚点可用 | 读备份内容确认是 `720`、非空、非当前文件的副本 |
| 4 原判据消除 | 自己跑 `config_precheck`，0 错误；并独立算了一遍 360 分钟窗口 |
| 5 无新增问题 | 对比改动前后的告警，确认 C2.0 是既有的 |
| 6 改了但没用？ | 分析参数是否会在运行时被覆盖 |

**没有采信自述**：每一条都有它自己读到的事实支撑，`diff` 和预检都是它自己跑的。

结论：**验证通过**，残留风险：无。

## 人工复核：结论对，但第 6 条的理由是错的

这份报告读起来很扎实，但它在第 6 条写了一句：

> 该参数为 WPS/NAMelist 静态配置，**运行时不会被其他机制覆盖**。

**这句是错的，而且错在本项目最核心的那个知识点上。**

WRF 源码 `share/input_wrf.F` L291：

```fortran
IF (switch == restart_only .AND. .NOT. override_restart_timers) THEN
```

`restart = .true.` 时，WRF **默认就是从重启文件恢复重启闹钟**，
namelist 里的 `restart_interval` **不生效**。这正是 [case-01](case-01-wrf-restart-alarm.md)
那次事故的真正机制，也是我们自己的预检工具 C1.1 规则在查的东西：

```
[✗] C1.1  热重启会覆盖 namelist 的 restart_interval，闹钟周期不可知
      restart = .true. 时 WRF 从重启文件恢复写重启闹钟，
      namelist 里的 restart_interval = 180 分钟不生效。
      依据: WRF/share/input_wrf.F L291
```

**这个沙盘之所以没事，是因为 `override_restart_timers = .true.` 恰好也在文件里
（第 17 行）—— 而 Verifier 通篇没有提到这个开关。**

也就是说：**如果那一行不在，它按同样的逻辑还会得出"无风险"，而那时候就是错的。**

### 这是"对了一半的机制"，第二次出现

[measure-04](measure-04-human-review-caught-a-wrong-mechanism.md) 里，
人工复核抓出 Triage 一个"对了一半"的因果机制。这次是同一类错误换了个 Agent：

| | measure-04 | 本次 |
|---|---|---|
| 谁 | Triage | Verifier |
| 结论 | 对 | 对 |
| 理由 | 错（把"跳过恢复"说成"override 生效"） | 错（把"默认会被覆盖"说成"不会被覆盖"） |
| 谁发现的 | 人工复核 | 人工复核 |

**两次都是结论对、机制错，两次都是人工复核抓出来的。**
这从两个方向说明问题：一是多 Agent 交叉验证**不是橡皮图章**，
二是**"知识入库需人工 review"这条边界不能取消**——
如果 Curator 把 Verifier 这段话直接写进 Runbook，就等于往知识库里注入了一条错误的领域知识。

### 第二处过度自信：验的是配置，不是结果

Verifier 写"残留风险：无"。但它验证的是**配置**，
而原始故障是**运行时**观察到的（跑满 6 小时、模式正常结束、零 wrfrst 产出）。

**配置看着对 ≠ 故障不会再犯。** 真正的验证需要一次短窗重跑，
观察 wrfrst 文件是否真的出现。这一点 Verifier 没有指出，
反而给了一个"无残留风险"的断言。

严格说，第 6 条正确的答案应该是：
**"配置层面无风险；但本次验证仅覆盖配置，运行时是否真的产出重启文件未经观察，
需一次短窗重跑确认。"**

## 由此产生的两条改动

1. **Verifier 的 SOUL 增加一条硬约束**：
   凡涉及"参数是否会在运行时生效"的判断，**必须引用源码或文档依据**，
   不得凭常识断言。给不出依据时应输出"无法验证"而不是"无风险"。
2. **Verifier 必须区分"配置层验证"与"运行时验证"**，
   并在报告里显式声明本次验证覆盖了哪一层。
   凡是原始故障在运行时才可观察的，配置层通过**不得**写成"残留风险：无"。

## 这次实跑改变了什么

| 项 | 之前 | 现在 |
|---|---|---|
| 闭环第 5 步 结果验证 | ❌ Verifier 未实跑 | ✅ 已实跑，六项清单独立复核 |
| 实跑 Agent 数 | 4 / 6 | **5 / 6** |
| "多 Agent 交叉验证有没有用" | 只是主张 | **有用，但不足以替代人工复核** —— 阴阳两组对照都有实例 |
| Verifier 会不会只会说 PASS | 未知 | **不会**：阴性对照判 FAIL，并戳穿了 Executor 自述里的假数字 |

## 阴性对照 · 给它一次「改了等于没改」的修复（incident-005）

一个只会说 PASS 的验证器毫无价值。所以立刻补了阴性对照：

构造一份配置，**表面上和 incident-002 一模一样**（同样 `restart_interval: 720 → 180`，
同样有回滚点、同样只改一行），但**故意不含 `override_restart_timers`** ——
也就是改了值却不生效，故障会原样复发。

Executor 的自述里还谎称"验证：改动已落盘，值在运行窗口内"。

### 结果：**验证不通过**，且理由完全正确

| # | 检查项 | 它的判定 |
|---|---|---|
| 1 | 改动落盘 | ✅ PASS |
| 2 | 与声称一致 | ✅ PASS（diff 仅一行） |
| 3 | 回滚点可用 | ✅ PASS |
| 4 | 原判据消除 | **❌ FAIL** |
| 5 | 无新增问题 | **❌ FAIL** |
| 6 | 改了但没用 | **⚠️ 有风险** |

**结论：验证不通过。**

它给出的机制这次是对的 —— 而且正是它上一次说错的那一条：

> `restart = .true.` 且缺少 `override_restart_timers = .true.`，
> WRF 在热重启模式下从 restart 文件恢复闹钟周期，
> namelist 中的 `restart_interval` **被忽略**。
> 上一个 restart 文件记录的周期是 720 分钟 > 360 分钟运行窗口 → 零 wrfrst 产出 → **故障复现**。

### 两个没要求它做、但它做了的动作

**一、当场戳穿了 Executor 的自述**：

> **预检报告 1 个错误，非 Executor 声称的"0 个错误"。**

这正是设立 Verifier 的全部意义 —— 自述不是证据。

**二、做了横向对比**：

> 对比 incident-002（同根因、已通过验证），其 namelist 包含 `override_restart_timers = .true.`，
> **这正是 incident-005 缺失的关键配置。**

它把两个 case 放在一起比，找出了差异项。这不在清单里，是它自己想到的。

### 但要如实说明一件事

这次它答对，**很大程度上是因为预检工具 C1.1 把答案直接摆在了它面前**
（C1.1 的输出里就写着 `override_restart_timers 未设置` 和源码依据 `input_wrf.F L291`）。
不能就此认为 Verifier 独立掌握了这个领域知识 ——
incident-002 那次预检是 0 错误、没有任何提示，它就把机制说反了。

**准确的结论是：Verifier 能可靠地把工具给出的判据转化为正确的验证结论，
但在工具沉默的地方，它的领域推理不可靠。**
这恰好也说明为什么本项目坚持"不赌模型做根因，只赌确定性的预检与判定"。

## 局限（不隐瞒）

1. **只跑了两个验证对象**（一阳性一阴性），不足以谈通过率与误判率。
2. 阴性对照那次，**答案是预检工具直接给出的**，未能验证 Verifier 在无工具提示时的判断力
   —— 而 incident-002 恰恰证明了那种情况下它会出错。
3. **未测"工具误报时 Verifier 会不会盲从"** —— 如果预检报了一个假错误，它会不会照样判 FAIL？
4. Curator 仍未实跑，第 8 步经验沉淀依然是 ⚠️。
